# Requirements Document

## Introduction

This spec ports the cook-smart barcode-scan-to-add-ingredient feature from the React Native app under `src/` to the Flutter app under `mobile/`. It is the third spec in the Flutter migration, immediately following `flutter-migration-architecture` (the Foundation_Phase, complete and shipped) and `flutter-port-auth` (the auth-port, complete and shipped). Every architectural decision committed by those two specs is inherited here without restatement except where a requirement below pins it explicitly.

Scope is the MVP "scan a barcode, look up the product, add the result to the user's pantry" path that the existing user-facing backend at `https://api.cooksmartapp.com` actually exposes today. Three external surfaces are involved:

1. The device camera, accessed via the foundation-pinned `mobile_scanner ^5.1.1` package (Foundation Requirement 10.3) on Android. iOS support is parked but not precluded.
2. The Open Food Facts public REST API at `https://world.openfoodfacts.org/api/v2/product/<barcode>.json`, free, unauthenticated, used to resolve a barcode to a product name, brand, category, and image URL.
3. The cook-smart REST API endpoint `POST /api/v1/ingredients`, authenticated with the JWT minted by the Auth_Feature, used to write the resolved product into the user's pantry.

Anything beyond "scan once, look up, add to pantry" is explicitly out of scope and deferred to later specs:

- Recipe matching and recipe suggestion based on the user's pantry are out of scope.
- The full ingredient-inventory CRUD surface (browse, edit, delete, expiration management) is out of scope. Only the "add via barcode" entry point lands in this spec.
- The cook-smart server-side `POST /api/v1/barcode/scan-to-pantry` and `GET /api/v1/barcode/lookup/:barcode` routes are visible in the backend code under `backend/src/routes/barcode.ts` and are intentionally **not** consumed by the Barcode_Feature, because the React Native predecessor calls Open Food Facts directly and the Flutter port preserves that contract per Foundation Requirement 9.3 (no backend changes).
- Cache-of-scanned-products persistence (the React Native `productLookupService` cache layer with smart expiration based on access count) is out of scope; a future spec may layer caching over the Riverpod provider seam this spec defines.
- iOS camera plumbing (`Info.plist` `NSCameraUsageDescription`, `Podfile` `mobile_scanner` integration, end-to-end build verification on a Mac) is out of scope per Foundation Requirement 7. The Barcode_Feature SHALL leave architectural hooks for iOS but SHALL NOT block on iOS verification.

Three facts discovered during code review anchor this spec and are formalised in the requirements below:

1. The cook-smart backend's `POST /api/v1/ingredients` endpoint expects a body shaped `{ customName, category, quantity, unit, expirationDate? }` (when adding by name rather than by an existing ingredient ID), authenticated by `authenticateToken` middleware. It returns a 201 with `{ message, ingredient }` and is **not** wrapped in the canonical `{ success, message, data }` envelope that Foundation Requirement 9.6 documents. This spec resolves the deviation at the feature boundary using the same feature-local-parsing approach the Auth_Feature established (Decision 1 of `flutter-port-auth/design.md`), rather than amending the foundation envelope.
2. The Open Food Facts v2 product endpoint returns a JSON document whose top-level `status` field is `1` for "product found" and `0` for "product not found", with the product fields nested under a top-level `product` key. The shape does not match the cook-smart envelope; this spec parses it inside a typed response class under `mobile/lib/features/barcode/data/` using the same `ServerException`-on-malformed-body discipline the Auth_Feature established (Auth Requirement 3.6).
3. The Auth_Feature's `AuthApiClient` seam pattern (Decision 4 of `flutter-port-auth/design.md`) is the established way to keep `package:dio` confined to `lib/core/network/` while exposing a feature-shaped transport surface. The Barcode_Feature follows the same pattern: an abstract `BarcodeApiClient` interface plus a Dio-backed `DioBarcodeApiClient` adapter, both under `lib/core/network/`, exposed via a feature-named `barcodeApiClientProvider`. This is the second instance of the pattern and confirms it as the established convention for future per-feature specs that need feature-shaped transport.

These requirements are derived from the user's MVP scope, the actual `backend/src/routes/ingredients.ts` contract, the existing React Native implementation (`src/components/barcode/BarcodeScannerModal.tsx`, `src/components/barcode/ManualBarcodeEntryModal.tsx`, `src/services/barcodeService.ts`, `src/services/productLookupService.ts`), the original `barcode-scanner` spec at `.kiro/specs/barcode-scanner/requirements.md`, and the Foundation_Phase and Auth_Feature published architectural commitments.

## Glossary

- **Barcode_Feature**: The Flutter barcode-scan-to-add-ingredient feature ported by this spec, residing under `mobile/lib/features/barcode/`.
- **Foundation_Phase**: The work committed by `.kiro/specs/flutter-migration-architecture/`, including the `core/` infrastructure layer, providers, and architectural-enforcement scripts. Cited as "Foundation Requirement N.M" or "Foundation Decision N".
- **Auth_Feature**: The work committed by `.kiro/specs/flutter-port-auth/`, including the `mobile/lib/features/auth/` source tree, the `AuthApiClient` transport seam, and the `authNotifierProvider` / `authStateProvider` provider pair. Cited as "Auth Requirement N.M" or "Auth Decision N".
- **Mobile_App**: The Flutter mobile app under `mobile/`, as defined by the Foundation_Phase.
- **Backend_API**: The cook-smart REST API at `https://api.cooksmartapp.com`, unchanged by this spec.
- **Open_Food_Facts_API**: The public Open Food Facts REST API at `https://world.openfoodfacts.org/api/v2/product/<barcode>.json`, free, unauthenticated, used to resolve a barcode to product metadata.
- **Ingredient_Endpoint**: The single Backend_API route this spec consumes, namely `POST /api/v1/ingredients`, authenticated via the `authenticateToken` middleware and accepting a body shaped per Requirement 5.
- **Barcode_Repository**: The data-layer repository at `mobile/lib/features/barcode/data/barcode_repository.dart` that orchestrates a scan session: validates a barcode, calls the Open_Food_Facts_API, and (on success) calls the Ingredient_Endpoint.
- **Barcode_Notifier**: The Riverpod notifier at `mobile/lib/features/barcode/presentation/barcode_notifier.dart` that owns the Scan_State sealed type and exposes `startSession`, `submitBarcode`, `confirmAdd`, and `reset` mutations.
- **Scan_State**: A sealed Dart type defined under `mobile/lib/features/barcode/domain/` with the variants `ScanIdle`, `ScanRequestingPermission`, `ScanPermissionDenied`, `ScanCameraActive`, `ScanLookingUp`, `ScanProductFound`, `ScanProductNotFound`, `ScanAdding`, `ScanAdded`, and `ScanFailed`.
- **Scan_Session**: A single instance of the user opening the scanner UI with the intent of resolving one barcode and adding the resulting product to the pantry. A Scan_Session begins on `startSession` and ends on `confirmAdd` succeeding, on `reset` being invoked, or on the scanner UI being dismissed.
- **Scanned_Product**: The Flutter domain model at `mobile/lib/features/barcode/domain/scanned_product.dart` representing the product resolved from the Open_Food_Facts_API for a given barcode, shaped per Requirement 7.
- **Ingredient_To_Add**: The Flutter domain model at `mobile/lib/features/barcode/domain/ingredient_to_add.dart` representing the body sent to the Ingredient_Endpoint, shaped per Requirement 7.
- **Off_Lookup_Response**: The typed response class at `mobile/lib/features/barcode/data/off_lookup_response.dart` that decodes the Open_Food_Facts_API response body into either a Scanned_Product or a "not found" sentinel.
- **Ingredient_Add_Response**: The typed response class at `mobile/lib/features/barcode/data/ingredient_add_response.dart` that decodes the Backend_API response body returned by `POST /api/v1/ingredients`.
- **Barcode_Api_Client**: The abstract transport seam at `mobile/lib/core/network/barcode_api_client.dart` plus its Dio-backed adapter, exposing `lookupOpenFoodFacts(barcode)` and `addIngredient(body)`. Modelled on the Auth_Feature's `AuthApiClient` seam (Auth Decision 4).
- **Camera_Permission_State**: An enum defined under `mobile/lib/features/barcode/domain/` with the variants `granted`, `denied`, `permanentlyDenied`, and `unavailable`, mirroring the four-way distinction the React Native `barcodeService` already makes.
- **Manual_Entry_Mode**: The fallback flow in which the user types a barcode into a text field instead of pointing the camera at one, used when camera permission is denied, the camera is unavailable, or the user prefers keyboard entry.

## Requirements

### Requirement 1: Feature Folder Layout

**User Story:** As the solo developer, I want every Barcode_Feature source file to live under `mobile/lib/features/barcode/` in the data/domain/presentation layout the Foundation_Phase committed and the Auth_Feature confirmed, so that the barcode code stays a deletable, move-able unit and the architectural-enforcement scripts pass without relaxation.

#### Acceptance Criteria

1. THE Barcode_Feature SHALL place every Dart source file under `mobile/lib/features/barcode/`, and SHALL place each file inside exactly one of the subfolders `data/`, `domain/`, or `presentation/`. EXCEPT THAT the transport seam files — `mobile/lib/core/network/barcode_api_client.dart` and its Dio-backed adapter — live under `lib/core/network/` so the Foundation_Phase's `tool/check_architecture.dart` ban on `package:dio` outside `lib/core/network/` continues to hold. The seam exposes only the Open_Food_Facts_API surface and the Ingredient_Endpoint surface; it is not a general-purpose API client. See Auth Decision 4 for the established pattern this requirement re-uses.
2. THE Barcode_Feature SHALL define the Scanned_Product domain model in `mobile/lib/features/barcode/domain/scanned_product.dart`, the Ingredient_To_Add domain model in `mobile/lib/features/barcode/domain/ingredient_to_add.dart`, the Scan_State sealed type in `mobile/lib/features/barcode/domain/scan_state.dart`, and the Camera_Permission_State enum in `mobile/lib/features/barcode/domain/camera_permission_state.dart`.
3. THE Barcode_Feature SHALL define the Barcode_Repository in `mobile/lib/features/barcode/data/barcode_repository.dart`, the Off_Lookup_Response class in `mobile/lib/features/barcode/data/off_lookup_response.dart`, and the Ingredient_Add_Response class in `mobile/lib/features/barcode/data/ingredient_add_response.dart`.
4. THE Barcode_Feature SHALL define the Barcode_Notifier in `mobile/lib/features/barcode/presentation/barcode_notifier.dart`, the `BarcodeScannerScreen` widget in `mobile/lib/features/barcode/presentation/barcode_scanner_screen.dart`, the `ManualBarcodeEntryScreen` widget in `mobile/lib/features/barcode/presentation/manual_barcode_entry_screen.dart`, and the `ScannedProductConfirmationScreen` widget in `mobile/lib/features/barcode/presentation/scanned_product_confirmation_screen.dart`.
5. THE Barcode_Feature SHALL NOT import any source file under `mobile/lib/features/<other_feature>/` and SHALL NOT be imported by any source file under `mobile/lib/features/<other_feature>/`. EXCEPT THAT the Barcode_Feature MAY read the Auth_Feature's `authNotifierProvider` and `authStateProvider` only via the foundation-exposed provider symbols re-exported from `mobile/lib/core/router/` and `mobile/lib/core/network/`; direct imports of files under `mobile/lib/features/auth/` are forbidden.
6. THE Barcode_Feature SHALL pass every invariant enforced by `mobile/tool/check_architecture.dart` without modification of that script, including but not limited to the bans on importing `package:dio` outside `lib/core/network/`, importing `package:flutter_secure_storage` outside `lib/core/storage/`, constructing `Dio(` or `GoRouter(` from a `presentation/` folder, and using `FutureBuilder` in any feature file.
7. THE Barcode_Feature SHALL NOT contain any `Color(` literal in any file under `mobile/lib/features/barcode/`, and any colour referenced by a presentation widget SHALL resolve to a constant defined in `lib/core/theme/app_colours.dart` per Foundation Requirement 8.4. The viewfinder corner colour, the loading indicator colour, the error banner colour, and the success banner colour SHALL each be drawn from a token in `app_colours.dart`, with new tokens added there if the existing palette lacks a suitable value.
8. THE Barcode_Feature SHALL provide a `_test.dart` file at the mirrored path under `mobile/test/features/barcode/` for every Dart source file under `mobile/lib/features/barcode/`, per Foundation Requirements 2.11 and 2.12.

### Requirement 2: Camera Permission and Hardware Lifecycle

**User Story:** As a user, I want the app to request camera access only when I tap the scan button, recover gracefully when I deny, and release the camera when I leave the scanner, so that the barcode feature works on Android today and is iOS-ready when iOS lands later.

#### Acceptance Criteria

1. WHEN the Mobile_App is first installed on an Android device, THE Barcode_Feature SHALL declare exactly one camera permission in `mobile/android/app/src/main/AndroidManifest.xml` using the literal string `<uses-permission android:name="android.permission.CAMERA" />`, and SHALL NOT declare any other camera-related permission (in particular, SHALL NOT declare `android.permission.READ_EXTERNAL_STORAGE`, `android.permission.WRITE_EXTERNAL_STORAGE`, or any image-gallery permission, because the Barcode_Feature does not read or write image files).
2. THE Barcode_Feature SHALL declare an iOS `NSCameraUsageDescription` placeholder string in `mobile/ios/Runner/Info.plist` with the literal value `"Cook Smart uses the camera to scan product barcodes."`, even though Foundation Requirement 7.3 forbids running iOS builds in CI; declaring the string keeps the iOS scaffold ready for a future spec without enabling iOS work today.
3. WHEN the user invokes the scan action and the Barcode_Notifier transitions out of `ScanIdle`, THE Barcode_Feature SHALL query the device's current Camera_Permission_State before activating the camera preview and SHALL NOT activate the camera preview when the state is anything other than `granted`.
4. WHEN the queried Camera_Permission_State is `denied` and has never been requested in the current install, THE Barcode_Feature SHALL request camera permission from the device operating system, using the `mobile_scanner ^5.1.1` package's permission integration where available and the platform's native permission API otherwise.
5. WHEN the queried or requested Camera_Permission_State is `permanentlyDenied`, THE Barcode_Feature SHALL transition the Scan_State to `ScanPermissionDenied` and SHALL surface a UI affordance that opens the device's app settings so the user can re-grant camera access manually.
6. WHEN the queried or requested Camera_Permission_State is `unavailable` (for example, the device has no camera hardware or the camera service is suspended), THE Barcode_Feature SHALL transition the Scan_State to `ScanPermissionDenied` with an "unavailable" sub-reason and SHALL still expose Manual_Entry_Mode as an alternative path.
7. WHILE the Barcode_Notifier is in `ScanCameraActive`, THE Barcode_Feature SHALL hold exactly one active camera preview, and SHALL release the camera within 500 milliseconds of any of the following events: the Scan_State transitioning out of `ScanCameraActive`, the BarcodeScannerScreen being popped from the router stack, the application lifecycle moving to the `paused` or `inactive` state.
8. WHEN the application lifecycle returns from `paused` to `resumed` while the user is on the BarcodeScannerScreen, THE Barcode_Feature SHALL re-activate the camera preview only when the Camera_Permission_State is still `granted`, and SHALL re-query the permission state before re-activation rather than assuming it.
9. THE Barcode_Feature SHALL NOT request camera permission, query camera permission state, or activate the camera preview before the user has explicitly invoked the scan action, so that the user is not prompted on app launch.
10. WHERE the iOS build flavour is enabled by a future spec, THE Barcode_Feature's permission-handling code SHALL be platform-agnostic to the extent that the underlying `mobile_scanner ^5.1.1` API permits, and SHALL NOT contain `if (Platform.isAndroid) ...` branches that would silently no-op on iOS without an explicit iOS implementation. Platform-specific behaviour, if any, SHALL be isolated behind an interface defined in `domain/` and implemented under `data/`.

### Requirement 3: Barcode Validation and Format Support

**User Story:** As a user, I want only real product barcodes to be accepted by the scanner and the manual-entry field, so that obvious garbage input is rejected before the network is consulted.

#### Acceptance Criteria

1. THE Barcode_Feature SHALL accept barcodes whose digit strings match the regular expression `^[0-9]{8,13}$` (between 8 and 13 ASCII digits inclusive, no whitespace, no leading or trailing characters) and SHALL reject every other input as an invalid barcode.
2. THE Barcode_Feature SHALL configure `mobile_scanner ^5.1.1` to detect at minimum the formats EAN-8, EAN-13, UPC-A, and UPC-E, matching the format set the React Native predecessor's `react-native-camera-kit` integration accepted, and SHALL NOT enable QR-code detection on the scanner because the cook-smart product database does not store QR-code-keyed products.
3. WHEN the camera detects a candidate barcode whose digit string does not match the regular expression in criterion 1, THE Barcode_Feature SHALL discard the candidate silently and SHALL NOT transition the Scan_State out of `ScanCameraActive`, so that misreads from poor lighting do not abort the session.
4. WHEN the user submits a manually entered barcode through Manual_Entry_Mode, THE Barcode_Feature SHALL validate the input against the regular expression in criterion 1 and SHALL render an inline field-level error stating "Barcode must be 8 to 13 digits" when the input is invalid, without invoking the Barcode_Repository.
5. IF a future requirement of this spec or a Per_Feature_Spec proposes accepting any barcode format other than EAN-8, EAN-13, UPC-A, and UPC-E, THEN the proposing requirement SHALL document the format, an Open_Food_Facts_API coverage note for that format, and a backend-side migration plan for storing the format if needed.

### Requirement 4: Open Food Facts Lookup Contract

**User Story:** As the solo developer, I want the Barcode_Repository to call exactly the Open_Food_Facts_API endpoint that resolves a barcode to a product and to parse the real response shape, so that the lookup ships against the live free service without ambiguous edge cases or backend coordination.

#### Acceptance Criteria

1. WHEN the Barcode_Notifier handles a confirmed-valid barcode, THE Barcode_Repository SHALL issue a `GET` to the URL `https://world.openfoodfacts.org/api/v2/product/<barcode>.json`, where `<barcode>` is the validated 8-to-13-digit string from Requirement 3.1, and SHALL set `requiresAuth` (the Foundation_Phase's `AuthInterceptor.requiresAuthExtraKey`) to `false` because the Open_Food_Facts_API does not authenticate.
2. THE Barcode_Repository SHALL apply a connect timeout of 5 seconds and a receive timeout of 10 seconds to every Open_Food_Facts_API request, overriding the foundation-default 10-second connect and 15-second receive timeouts (Foundation Requirement 4.5) for this endpoint only, because the Open_Food_Facts_API is a free best-effort service and a tight deadline keeps the user-perceived latency bounded. The override SHALL be applied per request via `Options(sendTimeout:..., receiveTimeout:...)` rather than mutating the global Dio instance.
3. WHEN a `200` response is received from the Open_Food_Facts_API, THE Barcode_Repository SHALL parse the response body as Off_Lookup_Response by reading the top-level field `status` (integer, expected values `0` or `1`) and the top-level field `product` (JSON object, present only when `status == 1`).
4. WHEN the parsed Off_Lookup_Response has `status == 1` and a non-null `product` object, THE Barcode_Repository SHALL extract the following fields from the `product` object: `product_name` (String, optional), `brands` (String, optional, comma-separated list of brand names), `categories` (String, optional, comma-separated list of category names), and `image_url` (String, optional). The Barcode_Repository SHALL produce a Scanned_Product with `name` set to the trimmed `product_name` value (or the literal string `"Unknown Product"` when `product_name` is null, missing, or empty after trimming), `brand` set to the first comma-separated entry of `brands` after trimming (or `null` when `brands` is null, missing, or empty), `category` set to the first comma-separated entry of `categories` after trimming (or `null`), and `imageUrl` set to `image_url` (or `null`).
5. WHEN the parsed Off_Lookup_Response has `status == 0`, or has `status == 1` but `product` is null or missing, THE Barcode_Repository SHALL resolve the lookup as a "product not found" outcome and SHALL NOT call any further Open_Food_Facts_API or Backend_API endpoint as part of the Scan_Session.
6. IF a successful HTTP response from the Open_Food_Facts_API is parsed and the parse fails because `status` is missing or not an integer, OR because `product` is present but is not a JSON object, OR because every field listed in criterion 4 is missing or non-string when present, THEN THE Barcode_Repository SHALL raise a `ServerException` with a message identifying the offending barcode and the offending field, following the same parse-strictness discipline the Auth_Feature established in Auth Requirement 3.6.
7. WHEN the Open_Food_Facts_API request fails with a `NetworkException` (no response received, timeout, connection error), THE Barcode_Repository SHALL surface the failure to the Barcode_Notifier as a `NetworkException` and SHALL NOT retry automatically; retry SHALL be initiated only by an explicit user action per Requirement 9.4.
8. WHEN the Open_Food_Facts_API responds with an HTTP status outside the 200-299 range, THE Barcode_Repository SHALL surface the failure as a `ServerException` whose message includes the HTTP status and the requested barcode, and SHALL NOT attempt to parse the response body as an Off_Lookup_Response.
9. THE Barcode_Repository SHALL NOT cache Open_Food_Facts_API responses to disk in this spec; the React Native predecessor's `productLookupService` cache layer (the `barcode_cache_*` AsyncStorage keys with smart expiration based on access count) is explicitly out of scope and is deferred to a future spec. The transport seam SHALL remain shaped such that adding a cache decorator under `data/` is a one-file change.
10. THE Barcode_Repository SHALL NOT consume the cook-smart Backend_API barcode routes `GET /api/v1/barcode/lookup/:barcode` or `POST /api/v1/barcode/scan-to-pantry`, because the React Native predecessor calls Open_Food_Facts directly and Foundation Requirement 9.3 forbids changing the Backend_API surface this migration consumes.

### Requirement 5: Cook-Smart Backend Ingredient Add Contract

**User Story:** As an authenticated user, I want the resolved scanned product to be persisted to my pantry by exactly the cook-smart endpoint the React Native app already consumes, so that the migration ships against the real backend without proposing endpoint changes.

#### Acceptance Criteria

1. WHEN the user confirms adding a Scanned_Product to the pantry, THE Barcode_Repository SHALL issue a `POST` to the path `/api/v1/ingredients` against the foundation-resolved Backend_API base URL, with `requiresAuth` set to `true` so the Foundation_Phase's `AuthInterceptor` attaches the JWT minted by the Auth_Feature.
2. THE Barcode_Repository SHALL build the request body from the Ingredient_To_Add domain model with exactly the following JSON fields, all camelCase to match the existing React Native client and `backend/src/routes/ingredients.ts` POST handler: `customName` (String, the Scanned_Product's resolved name), `category` (String, the Scanned_Product's resolved category or the literal string `"other"` when no category was resolved), `quantity` (Number, defaulting to `1` when the user does not override), `unit` (String, defaulting to `"piece"` when the user does not override), and `notes` (String, set to the literal pattern `"Added via barcode scan (<barcode>)"` so the React Native pantry's existing audit trail is preserved). The body SHALL NOT include `ingredientId`, `expirationDate`, or any other field, because the Scanned_Product is by definition new to the user and expiration management is out of scope.
3. THE Barcode_Repository SHALL accept any HTTP success response in the range 200 through 299 inclusive as a successful add, with 201 being the expected status returned by `backend/src/routes/ingredients.ts`'s POST handler.
4. WHEN a `201` response is received from the Ingredient_Endpoint, THE Barcode_Repository SHALL parse the response body as Ingredient_Add_Response by reading the top-level field `message` (String) and the top-level field `ingredient` (JSON object, optional). The Barcode_Repository SHALL NOT attempt to parse the response as the Foundation_Phase's canonical `{ success, message, data }` envelope, because the Ingredient_Endpoint does not return that envelope, applying the same feature-local parsing approach Auth Decision 1 established for the auth endpoints.
5. WHEN the parsed Ingredient_Add_Response indicates success, THE Barcode_Repository SHALL resolve the operation with no further side effects on `SecureStorage` and SHALL NOT cache the added ingredient locally in this spec.
6. IF a successful HTTP response from the Ingredient_Endpoint is parsed and the parse fails because `message` is missing or non-string, THEN THE Barcode_Repository SHALL still resolve the operation as success when the HTTP status is 200 or 201, because the user-visible add-to-pantry side effect has already occurred on the backend; the Barcode_Repository SHALL surface the malformed-body fact only to a logging hook, not to the Barcode_Notifier.
7. WHEN the Ingredient_Endpoint responds with `400` and a body containing `{ error, details }` (the Express-validator failure shape used by `backend/src/routes/ingredients.ts`), THE Barcode_Repository SHALL surface the failure as a `ValidationException` whose message is built from the response's `error` field followed by a comma-separated summary of the `details` array, and SHALL NOT retry the request.
8. WHEN the Ingredient_Endpoint responds with `401`, THE Foundation_Phase's `ErrorInterceptor` SHALL run its existing clear-and-redirect path (Foundation Requirement 4.10) per the Auth_Feature's wiring (Auth Requirement 7.3), and the Barcode_Repository SHALL surface the resulting `UnauthorisedException` to the Barcode_Notifier, which SHALL transition Scan_State to `ScanFailed` with a session-expired sub-reason. No backend changes are required to support this behaviour because the Auth_Feature's overrides already close the loop.
9. WHEN the Ingredient_Endpoint responds with `500` or any other 5xx status, THE Barcode_Repository SHALL surface the failure as a `ServerException` whose message includes the HTTP status and the requested barcode for diagnostic clarity.
10. THE Barcode_Repository SHALL NOT issue a request to any path other than `/api/v1/ingredients` against the Backend_API. The Backend_API routes `POST /api/v1/ingredients/custom`, `GET /api/v1/ingredients/search`, `POST /api/v1/ingredients/pantry`, and `POST /api/v1/barcode/scan-to-pantry` are out of scope for this spec.

### Requirement 6: Authenticated-Request Precondition

**User Story:** As the solo developer, I want the barcode scanner to require an authenticated user before the camera even starts, so that an unauthenticated user is redirected to login rather than scanning a barcode they have no session to persist.

#### Acceptance Criteria

1. WHEN the user attempts to enter the BarcodeScannerScreen via any router path, THE Foundation_Phase's `routerProvider` SHALL apply its existing redirect rule (Foundation Requirement 5.7) and SHALL redirect an unauthenticated user to `/auth/login` before the BarcodeScannerScreen widget is constructed. The Barcode_Feature SHALL NOT add a custom redirect rule to the router; it SHALL rely on the Auth_Feature's `authStateProvider` override (Auth Requirement 7.2) to drive the existing rule.
2. WHEN the Barcode_Notifier transitions to `ScanIdle`, THE Barcode_Feature SHALL read the Auth_Feature's `authNotifierProvider` to confirm the current Auth_State is `AuthAuthenticated`, and SHALL transition Scan_State to `ScanFailed` with a "not authenticated" sub-reason when the Auth_State is anything else. This is a defence-in-depth check; the router redirect of criterion 1 is the primary gate.
3. WHILE a Scan_Session is in flight, IF the Auth_Notifier emits `AuthUnauthenticated` for any reason (including a 401 from the Ingredient_Endpoint per Requirement 5.8, an explicit logout from another screen, or a Session_Restore failure), THEN THE Barcode_Notifier SHALL transition the Scan_State to `ScanFailed` with a session-expired sub-reason and SHALL release the camera per Requirement 2.7.
4. THE Barcode_Repository SHALL NOT persist or read the JWT directly from `SecureStorage`. The JWT SHALL be attached to outgoing requests exclusively by the Foundation_Phase's `AuthInterceptor` per Foundation Requirement 4.2, with the Barcode_Repository setting `requiresAuth: true` per Requirement 5.1.
5. THE Barcode_Repository SHALL NOT import any source file under `mobile/lib/features/auth/` directly; it SHALL interact with auth state only through the foundation-exposed `authNotifierProvider` symbol (re-exported by the Auth_Feature into a foundation-visible location per Auth Requirement 7) and through the `requiresAuth` flag on outgoing requests.

### Requirement 7: Domain Models

**User Story:** As the solo developer, I want one Scanned_Product type that captures every field this spec consumes from the Open_Food_Facts_API and one Ingredient_To_Add type that captures every field the Ingredient_Endpoint accepts, so that the boundary between transport and presentation is type-checked.

#### Acceptance Criteria

1. THE Scanned_Product domain model SHALL declare the following non-null fields: `barcode` (String, the validated 8-to-13-digit string from Requirement 3.1), `name` (String, the resolved product name per Requirement 4.4).
2. THE Scanned_Product domain model SHALL declare the following nullable fields: `brand` (String?), `category` (String?), `imageUrl` (String?).
3. THE Scanned_Product domain model SHALL be implemented as a `final class` with `const` constructor, value-equality (`==` and `hashCode` by all fields), and `copyWith` covering every field declared in criteria 1 and 2.
4. THE Ingredient_To_Add domain model SHALL declare the following non-null fields: `barcode` (String), `customName` (String), `category` (String), `quantity` (num), `unit` (String). It SHALL provide a method `toBackendJson()` that emits the JSON body shape mandated by Requirement 5.2 with the `notes` field synthesised from `barcode` per the literal pattern in that requirement.
5. THE Ingredient_To_Add domain model SHALL provide a factory `Ingredient_To_Add.fromScannedProduct(Scanned_Product, {num quantity = 1, String unit = 'piece'})` that maps a Scanned_Product to a default-shaped Ingredient_To_Add, applying the rule "category defaults to the literal string `'other'` when the Scanned_Product's category is null". The user-confirmation flow MAY override `quantity` and `unit` before calling `toBackendJson()`.
6. THE Scan_State sealed type SHALL declare exactly ten variants in this order: `ScanIdle` (no payload), `ScanRequestingPermission` (no payload), `ScanPermissionDenied` (a `reason` field of an enum sub-type with values `denied`, `permanentlyDenied`, and `unavailable`), `ScanCameraActive` (no payload), `ScanLookingUp` (a `barcode` String field), `ScanProductFound` (a `Scanned_Product` field), `ScanProductNotFound` (a `barcode` String field), `ScanAdding` (an `Ingredient_To_Add` field), `ScanAdded` (an optional `addedIngredientName` String field, populated from the Ingredient_Add_Response per Requirement 5.4 when available), and `ScanFailed` (a `reason` enum sub-type field with values `network`, `server`, `validation`, `notAuthenticated`, `sessionExpired`, `cameraUnavailable`, plus a `description` String field).
7. THE Scan_State sealed parent and each of its ten variants SHALL be implemented as `final class` with `const` constructor and value-equality, so that the Riverpod notifier emits `==`-equal states without re-rendering when nothing has changed.
8. IF a `product` JSON object received from the Open_Food_Facts_API is missing every field listed in Requirement 4.4, THEN the Off_Lookup_Response SHALL still construct a Scanned_Product whose `name` is the literal string `"Unknown Product"`, because the React Native predecessor's behaviour is to surface "Unknown Product" rather than to fail; this is a deliberate UX trade-off and is preserved here for parity.

### Requirement 9: Barcode Scanning UX

**User Story:** As a user, I want a clear and forgiving scanner UI that gives me feedback the moment a barcode is read and lets me bail out to manual entry whenever I want, so that I can add an ingredient quickly even when scanning is awkward.

#### Acceptance Criteria

1. WHEN the BarcodeScannerScreen is constructed and the Camera_Permission_State is `granted`, THE BarcodeScannerScreen SHALL render a full-screen camera preview with a centred rectangular viewfinder overlay measuring 250 logical pixels on a side, with four corner markers drawn in a colour token from `app_colours.dart`, and SHALL display the instruction text `"Point camera at barcode"` below the viewfinder.
2. WHEN the camera detects a candidate barcode that passes the validation rule of Requirement 3.1, THE Barcode_Feature SHALL transition Scan_State to `ScanLookingUp` within 100 milliseconds of detection, SHALL trigger a single haptic-feedback impulse of "medium" intensity, and SHALL render a non-blocking loading card with the text `"Looking up product..."` centred on the screen.
3. WHILE the Scan_State is `ScanLookingUp`, THE Barcode_Feature SHALL ignore further barcode-detection callbacks from the camera, so that a single barcode visible in frame for several frames is not looked up multiple times. This SHALL be implemented as a debounce in the Barcode_Notifier rather than by stopping the camera, so that the camera does not need to be restarted on a "try again" outcome.
4. WHEN the Scan_State transitions to `ScanProductNotFound`, THE Barcode_Feature SHALL render a modal alert with the title `"Product Not Found"`, the body `"This product is not in our database. You can add it manually."`, and exactly two action buttons: `"Manual Entry"` (which closes the alert and pushes the ManualBarcodeEntryScreen) and `"Try Again"` (which transitions Scan_State back to `ScanCameraActive`).
5. WHEN the Scan_State transitions to `ScanProductFound`, THE Barcode_Feature SHALL push the ScannedProductConfirmationScreen, which SHALL display the Scanned_Product's `name`, `brand` (when non-null), `category` (when non-null), and `imageUrl` rendered via `cached_network_image ^3.3.1` (Foundation Requirement 10.7) when non-null, plus editable fields for `quantity` (default `1`) and `unit` (default `"piece"`), plus an `"Add to Pantry"` button.
6. WHEN the user taps `"Add to Pantry"` on the ScannedProductConfirmationScreen, THE Barcode_Feature SHALL transition Scan_State to `ScanAdding`, SHALL invoke the Barcode_Repository's `addIngredient` operation per Requirement 5.1, and SHALL disable the `"Add to Pantry"` button until the operation resolves.
7. WHEN the Scan_State transitions to `ScanAdded`, THE Barcode_Feature SHALL render a non-blocking success banner with the text `"<addedIngredientName> has been added to your inventory"` (using the value from Requirement 7.6 when available, falling back to the Scanned_Product's `name` otherwise) and SHALL pop the BarcodeScannerScreen, ScannedProductConfirmationScreen, and any associated modals from the router stack within 1 second.
8. THE BarcodeScannerScreen SHALL render exactly two control buttons at the bottom of the screen at all times: `"Cancel"` (which pops the BarcodeScannerScreen) and `"Manual Entry"` (which closes the camera and pushes the ManualBarcodeEntryScreen). The buttons SHALL remain interactive in every Scan_State except `ScanAdding`.
9. WHEN the user navigates away from the BarcodeScannerScreen by tapping `"Cancel"`, by using the system back gesture, or by switching apps, THE Barcode_Feature SHALL transition Scan_State to `ScanIdle`, release the camera per Requirement 2.7, and dispose the BarcodeNotifier per Requirement 8.7.
10. THE BarcodeScannerScreen and the ManualBarcodeEntryScreen SHALL NOT use a `FutureBuilder` to render any state, because Foundation Requirement 3.6 forbids it and the architecture script enforces the ban; every async piece of state SHALL be expressed as an `AsyncValue<T>` Riverpod provider read with `AsyncValue<T>.when`.

### Requirement 10: Manual-Entry Fallback

**User Story:** As a user whose camera is denied, broken, or just inconvenient right now, I want to type a barcode in by hand and have the same lookup-and-add flow run, so that I am not blocked from adding an ingredient.

#### Acceptance Criteria

1. THE ManualBarcodeEntryScreen SHALL render a single text field that accepts only ASCII digits (filtered at the input level so non-digit characters are silently dropped on insertion), with `keyboardType` set to numeric, `maxLength` set to 13, and the label `"Enter Barcode"`.
2. THE ManualBarcodeEntryScreen SHALL render a `"Lookup Product"` submit button that is disabled while the input field is empty and while the Scan_State is `ScanLookingUp`.
3. WHEN the user submits a manually entered barcode, THE Barcode_Notifier SHALL apply the validation rule of Requirement 3.1 first; IF validation fails, THEN THE Barcode_Notifier SHALL render an inline error per Requirement 3.4, SHALL NOT transition Scan_State to `ScanLookingUp`, and SHALL NOT invoke the Open_Food_Facts_API lookup; otherwise THE Barcode_Notifier SHALL transition Scan_State to `ScanLookingUp` and invoke the same Open_Food_Facts_API lookup the camera path uses per Requirement 4.
4. WHEN a manually entered barcode resolves to `ScanProductFound`, THE Barcode_Feature SHALL push the ScannedProductConfirmationScreen, with the same UX defined in Requirement 9.5, so that camera-scanned and manually-entered confirmations share one code path.
5. WHEN a manually entered barcode resolves to `ScanProductNotFound`, THE ManualBarcodeEntryScreen SHALL render an inline non-blocking message with the text `"Product not found in the Open Food Facts database. Try a different barcode or add the ingredient by hand from the pantry screen."`, leaving the input field populated so the user can correct a typo, and SHALL NOT invoke the modal alert defined in Requirement 9.4 (because the modal-with-Try-Again interaction does not apply when there is no live camera to retry with).
6. THE Barcode_Feature SHALL make the ManualBarcodeEntryScreen reachable from every Scan_State except `ScanAdding`, regardless of the Camera_Permission_State; the established entry paths are the BarcodeScannerScreen's `"Manual Entry"` button per Requirement 9.8 and the BarcodeScannerScreen's `"Open Settings"` affordance per Requirement 2.5 when camera permission is `permanentlyDenied`. Future entry paths added to the Mobile_App (for example, a pantry-screen "Add by barcode" shortcut) SHALL push the ManualBarcodeEntryScreen using the same `barcodeNotifierProvider` so a single Barcode_Notifier instance is reused across paths.
7. WHEN the ManualBarcodeEntryScreen is the only entry path because the Camera_Permission_State is `unavailable` per Requirement 2.6, THE Barcode_Feature SHALL render an informational note above the input field with the text `"Camera is unavailable; enter the barcode by hand."`, so the user understands why the camera path is missing.

### Requirement 11: Error Handling Matrix

**User Story:** As a user, I want every failure mode to surface a clear message and a recovery action, so that I am never stuck staring at a blank screen.

#### Acceptance Criteria

1. WHEN Camera_Permission_State is `denied` (one-time refusal), THE Barcode_Feature SHALL render an inline error region on the BarcodeScannerScreen with the text `"Camera access is needed to scan barcodes."` and a `"Grant Permission"` button that re-invokes the permission request flow per Requirement 2.4.
2. WHEN Camera_Permission_State is `permanentlyDenied` (the user has selected "Don't ask again" or has denied at the OS level), THE Barcode_Feature SHALL render an inline error region with the text `"Camera access is blocked. Please enable it in Settings."` and an `"Open Settings"` button that calls the device settings page via the foundation-pinned `url_launcher ^6.3.0` package (Foundation Requirement 10.6).
3. WHEN Camera_Permission_State is `unavailable`, THE Barcode_Feature SHALL render an inline error region with the text `"Camera is not available on this device."`, SHALL NOT render the camera preview, SHALL NOT render the `"Grant Permission"` button, and SHALL navigate the user toward the ManualBarcodeEntryScreen as the primary action per Requirement 10.7.
4. WHEN the Open_Food_Facts_API request fails with `NetworkException`, THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `network` and SHALL render a modal alert with the title `"Lookup Failed"`, a body identifying the failure as a network error, and exactly two action buttons: `"Retry"` (which re-invokes the lookup with the same barcode) and `"Manual Entry"` (which pushes the ManualBarcodeEntryScreen with the barcode pre-populated).
5. WHEN the Open_Food_Facts_API request fails with `ServerException` per Requirement 4.6 or 4.8, THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `server` and SHALL render a modal alert with the title `"Lookup Failed"`, a body identifying the failure as a server error, and the same two action buttons defined in criterion 4.
6. WHEN the Ingredient_Endpoint request fails with `ValidationException` per Requirement 5.7, THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `validation` and SHALL render the validation message in an inline error region on the ScannedProductConfirmationScreen, leaving the user's typed `quantity` and `unit` values intact so the user can correct them.
7. WHEN the Ingredient_Endpoint request fails with `UnauthorisedException` per Requirement 5.8 (a 401 that survives the foundation's clear-and-redirect path), THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `sessionExpired`, and the foundation's `routerProvider` SHALL redirect to `/auth/login` per Foundation Requirement 5.9 driven by the Auth_Notifier emitting `AuthUnauthenticated` per Auth Requirement 8.4. The Barcode_Feature SHALL NOT render its own session-expired modal because the redirect renders the LoginScreen with the Auth_Feature's existing inline error.
8. WHEN the Ingredient_Endpoint request fails with `ServerException` per Requirement 5.9, THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `server` and SHALL render a modal alert on the ScannedProductConfirmationScreen with the title `"Add Failed"`, a body identifying the failure as a server error, and a `"Retry"` button that re-invokes `addIngredient` with the same Ingredient_To_Add.
9. THE Barcode_Feature SHALL NOT render the literal text of an underlying `DioException`, an HTTP status code by itself, or a stack trace anywhere in the user-facing UI; every error message rendered to the user SHALL come from the static strings enumerated in this Requirement, from the Auth_Feature's existing strings (for session-expired), or from the Backend_API's `error` and `details` fields (for `ValidationException` per Requirement 5.7).
10. THE Barcode_Feature SHALL emit every captured error to the foundation-pinned Firebase Crashlytics integration (Foundation Requirement 16) via `FlutterError.onError` and `PlatformDispatcher.instance.onError` paths the foundation already registered, by allowing `ServerException`, `NetworkException`, `ValidationException`, and `UnauthorisedException` to propagate to those handlers as non-fatal Dart errors. The Barcode_Feature SHALL NOT directly call any Crashlytics API; it SHALL rely on the foundation's existing wiring.

### Requirement 12: Performance and Responsiveness

**User Story:** As a user, I want the scanner to be snappy and the lookups to be bounded, so that the feature feels production-grade rather than experimental.

#### Acceptance Criteria

1. WHEN the user invokes the scan action and the Camera_Permission_State is already `granted`, THE Barcode_Feature SHALL initiate camera activation within 2 seconds of the action and SHALL render a loading indicator if the camera preview has not produced its first frame after that interval, matching the React Native predecessor's documented activation budget. IF the underlying device or `mobile_scanner ^5.1.1` plumbing exceeds 2 seconds because of a constraint outside the Barcode_Feature's control (a slow camera-service handshake, an unusually cold start, or the OS deferring the camera grant), THEN THE Barcode_Feature SHALL still complete activation when the camera becomes available rather than abandon the session, and SHALL transition Scan_State to `ScanFailed` with sub-reason `cameraUnavailable` only when the underlying API itself surfaces a hard failure.
2. WHEN the camera detects a valid barcode in frame, THE Barcode_Feature SHALL transition Scan_State to `ScanLookingUp` within 100 milliseconds of the detection callback, per Requirement 9.2.
3. THE Barcode_Feature SHALL apply the per-request timeout overrides defined in Requirement 4.2 (5-second connect, 10-second receive) to every Open_Food_Facts_API call, so a slow free-tier response surfaces as a `NetworkException` after at most 10 seconds rather than after the foundation-default 15 seconds.
4. THE Barcode_Feature SHALL apply the foundation-default timeouts (10-second connect, 15-second receive per Foundation Requirement 4.5) to every Ingredient_Endpoint call, because the cook-smart Backend_API is the same surface the Auth_Feature consumes and the timeouts SHALL be uniform across cook-smart endpoints.
5. THE Barcode_Feature SHALL debounce barcode-detection callbacks per Requirement 9.3 such that after a valid detection, no further detection callback SHALL trigger another lookup until either the Scan_State has returned to `ScanCameraActive` (via "Try Again") or the BarcodeScannerScreen has been popped and re-pushed.
6. THE Barcode_Feature SHALL apply a soft rate limit of at most one Open_Food_Facts_API request per 1000 milliseconds per Scan_Session, matching the React Native predecessor's `MIN_REQUEST_INTERVAL` constant, so that rapid re-scans (the user pointing the camera at one barcode after another in quick succession) do not exceed the free-tier service's expected request cadence.
7. THE Barcode_Feature SHALL release the camera within 500 milliseconds of leaving `ScanCameraActive` per Requirement 2.7, so that the device's camera hardware is not held in the suspended state for an extended period after navigation.

### Requirement 2: Camera Permission and Hardware Lifecycle

**User Story:** As a user, I want the app to request camera access only when I tap the scan button, recover gracefully when I deny, and release the camera when I leave the scanner, so that the barcode feature works on Android today and is iOS-ready when iOS lands later.

#### Acceptance Criteria

1. WHEN the Mobile_App is first installed on an Android device, THE Barcode_Feature SHALL declare exactly one camera permission in `mobile/android/app/src/main/AndroidManifest.xml` using the literal string `<uses-permission android:name="android.permission.CAMERA" />`, and SHALL NOT declare any other camera-related permission (in particular, SHALL NOT declare `android.permission.READ_EXTERNAL_STORAGE`, `android.permission.WRITE_EXTERNAL_STORAGE`, or any image-gallery permission, because the Barcode_Feature does not read or write image files).
2. THE Barcode_Feature SHALL declare an iOS `NSCameraUsageDescription` placeholder string in `mobile/ios/Runner/Info.plist` with the literal value `"Cook Smart uses the camera to scan product barcodes."`, even though Foundation Requirement 7.3 forbids running iOS builds in CI; declaring the string keeps the iOS scaffold ready for a future spec without enabling iOS work today.
3. WHEN the user invokes the scan action and the Barcode_Notifier transitions out of `ScanIdle`, THE Barcode_Feature SHALL query the device's current Camera_Permission_State within 200 milliseconds before activating the camera preview and SHALL NOT activate the camera preview when the queried state is anything other than `granted`.
4. WHEN the queried Camera_Permission_State is `denied` and a persisted boolean flag `cameraPermissionEverRequested` (initialised to `false` on first install, set to `true` immediately after any permission request returns) is `false`, THE Barcode_Feature SHALL request camera permission from the device operating system using the `mobile_scanner ^5.1.1` package's permission integration where available and the platform's native permission API otherwise, and SHALL set `cameraPermissionEverRequested` to `true` upon receiving any response from the request.
5. IF the queried or requested Camera_Permission_State is `permanentlyDenied`, THEN THE Barcode_Feature SHALL transition the Scan_State to `ScanPermissionDenied` within 200 milliseconds and SHALL render an "Open Settings" button labelled with the literal text `"Open Settings"` plus an explanatory message above the button so the user can re-grant camera access manually.
6. IF the queried or requested Camera_Permission_State is `unavailable` (the device has no camera hardware or the camera service is suspended), THEN THE Barcode_Feature SHALL transition the Scan_State to `ScanPermissionDenied` with an `unavailable` sub-reason within 200 milliseconds and SHALL still expose Manual_Entry_Mode as an alternative path per Requirement 10.7.
7. WHILE the Barcode_Notifier is in `ScanCameraActive`, THE Barcode_Feature SHALL hold exactly one active camera preview.
8. WHEN any of the following events occurs — the Scan_State transitioning out of `ScanCameraActive`, the BarcodeScannerScreen being popped from the router stack, the application lifecycle moving to the `paused` or `inactive` state — THE Barcode_Feature SHALL release the camera within 500 milliseconds of the event.
9. WHEN the application lifecycle returns from `paused` to `resumed` while the user is on the BarcodeScannerScreen, THE Barcode_Feature SHALL re-query the Camera_Permission_State before re-activation, and SHALL re-activate the camera preview only when the re-queried state is `granted`.
10. IF the application lifecycle returns from `paused` to `resumed` while the user is on the BarcodeScannerScreen and the re-queried Camera_Permission_State is anything other than `granted`, THEN THE Barcode_Feature SHALL transition the Scan_State to the appropriate `ScanPermissionDenied` variant per criteria 5 or 6 within 200 milliseconds rather than re-activating the camera.
11. THE Barcode_Feature SHALL NOT request camera permission, query camera permission state, or activate the camera preview before the user has explicitly invoked the scan action, so that the user is not prompted on app launch.
12. WHERE the iOS build flavour is enabled by a future spec, THE Barcode_Feature's permission-handling code SHALL be platform-agnostic to the extent that the `mobile_scanner ^5.1.1` package's documented public API permits, and SHALL NOT contain `if (Platform.isAndroid) ...` branches that would silently no-op on iOS without an explicit iOS implementation. Platform-specific behaviour, if any, SHALL be isolated behind an interface defined in `domain/` and implemented under `data/`.

### Requirement 3: Barcode Validation and Format Support

**User Story:** As a user, I want only real product barcodes to be accepted by the scanner and the manual-entry field, so that obvious garbage input is rejected before the network is consulted.

#### Acceptance Criteria

1. THE Barcode_Feature SHALL accept barcodes whose digit strings match the regular expression `^[0-9]{8,13}$` (between 8 and 13 ASCII digits inclusive, no whitespace, no leading or trailing characters) and SHALL reject every other input as an invalid barcode.
2. THE Barcode_Feature SHALL configure `mobile_scanner ^5.1.1` to detect at minimum the formats EAN-8, EAN-13, UPC-A, and UPC-E, matching the format set the React Native predecessor's `react-native-camera-kit` integration accepted, and SHALL NOT enable QR-code detection on the scanner because the cook-smart product database does not store QR-code-keyed products.
3. WHEN the camera detects a candidate barcode whose digit string does not match the regular expression in criterion 1, THE Barcode_Feature SHALL discard the candidate without rendering any error to the user, SHALL NOT transition the Scan_State out of `ScanCameraActive`, and SHALL keep the Scan_Session active for at least 30 seconds before any timeout-based session termination, so that misreads from poor lighting do not abort the session.
4. WHEN the user submits a manually entered barcode through Manual_Entry_Mode that matches the regular expression in criterion 1, THE Barcode_Feature SHALL forward the barcode to the Barcode_Repository within 200 milliseconds of submission per Requirement 10.3.
5. IF the user submits a manually entered barcode through Manual_Entry_Mode that does not match the regular expression in criterion 1, THEN THE Barcode_Feature SHALL render an inline field-level error stating the literal text `"Barcode must be 8 to 13 digits"`, SHALL preserve the user's typed input verbatim in the input field, SHALL NOT invoke the Barcode_Repository, and SHALL keep Manual_Entry_Mode active so the user can correct and resubmit.
6. WHEN the user types or pastes any non-digit character into the Manual_Entry_Mode input field, THE Barcode_Feature SHALL silently drop those characters at the input level so the input field's value contains only ASCII digits at all times.
7. IF a future requirement of this spec or a Per_Feature_Spec proposes accepting any barcode format other than EAN-8, EAN-13, UPC-A, and UPC-E, THEN the proposing requirement SHALL document the format, an Open_Food_Facts_API coverage note for that format, and a backend-side migration plan for storing the format if needed.

### Requirement 4: Open Food Facts Lookup Contract

**User Story:** As the solo developer, I want the Barcode_Repository to call exactly the Open_Food_Facts_API endpoint that resolves a barcode to a product and to parse the real response shape, so that the lookup ships against the live free service without ambiguous edge cases or backend coordination.

#### Acceptance Criteria

1. WHEN the Barcode_Notifier handles a confirmed-valid barcode, THE Barcode_Repository SHALL issue a `GET` to the URL `https://world.openfoodfacts.org/api/v2/product/<barcode>.json`, where `<barcode>` is the validated 8-to-13-digit string from Requirement 3.1, and SHALL set `requiresAuth` (the Foundation_Phase's `AuthInterceptor.requiresAuthExtraKey`) to `false` because the Open_Food_Facts_API does not authenticate.
2. THE Barcode_Repository SHALL apply a connect timeout of 5 seconds and a receive timeout of 10 seconds to every Open_Food_Facts_API request, overriding the foundation-default 10-second connect and 15-second receive timeouts (Foundation Requirement 4.5) for this endpoint only. The override SHALL be applied per request via `Options(sendTimeout:..., receiveTimeout:...)` rather than mutating the global Dio instance.
3. WHEN a `200` response is received from the Open_Food_Facts_API and the response body is at most 512 KiB in size, THE Barcode_Repository SHALL parse the response body as Off_Lookup_Response by reading the top-level field `status` (integer, expected values `0` or `1`) and the top-level field `product` (JSON object, present only when `status == 1`). IF the response body exceeds 512 KiB, THEN THE Barcode_Repository SHALL raise a `ServerException` whose message identifies the offending barcode and the size limit breach, and SHALL NOT attempt to parse the body.
4. WHEN the parsed Off_Lookup_Response has `status == 1` and a non-null `product` object, THE Barcode_Repository SHALL extract the following fields from the `product` object, applying the corresponding length caps and trimming rules:
   - `product_name` (String, optional, maximum 200 characters after trimming): the Scanned_Product's `name` SHALL be set to the trimmed value, or to the literal string `"Unknown Product"` when `product_name` is null, missing, empty after trimming, or longer than 200 characters after trimming.
   - `brands` (String, optional, maximum 200 characters after trimming, comma-separated): the Scanned_Product's `brand` SHALL be set to the first comma-separated entry of `brands` after trimming, or to `null` when `brands` is null, missing, empty after trimming, or longer than 200 characters after trimming.
   - `categories` (String, optional, maximum 200 characters after trimming, comma-separated): the Scanned_Product's `category` SHALL be set to the first comma-separated entry of `categories` after trimming, or to `null` when `categories` is null, missing, empty after trimming, or longer than 200 characters after trimming.
   - `image_url` (String, optional, maximum 2048 characters): the Scanned_Product's `imageUrl` SHALL be set to the value verbatim, or to `null` when `image_url` is null, missing, empty, or longer than 2048 characters.
5. WHEN the parsed Off_Lookup_Response has `status == 0`, or has `status == 1` but `product` is null, missing, or not a JSON object, THE Barcode_Repository SHALL resolve the lookup as a typed `ProductNotFound` outcome distinguishable from both success (a valid Scanned_Product) and failure (a raised exception), SHALL NOT call any further Open_Food_Facts_API or Backend_API endpoint as part of the Scan_Session, and the Barcode_Notifier SHALL observe the typed outcome to transition Scan_State to `ScanProductNotFound`.
6. IF a successful HTTP response from the Open_Food_Facts_API is parsed and the parse fails because `status` is missing, not an integer, or an integer outside the set `{0, 1}`, OR because the top-level body is not a JSON object, OR because `product` is present but is not a JSON object, THEN THE Barcode_Repository SHALL raise a `ServerException` with a message identifying the offending barcode and the offending field, SHALL NOT produce a Scanned_Product, and SHALL NOT produce a `ProductNotFound` outcome.
7. WHEN the Open_Food_Facts_API request fails with a transport-level error (connect timeout per criterion 2, receive timeout per criterion 2, DNS failure, connection refused, TLS handshake failure), THE Barcode_Repository SHALL surface the failure to the Barcode_Notifier as a `NetworkException` whose message identifies the failure category and the offending barcode, SHALL NOT retry automatically, and retry SHALL be initiated only by an explicit user action per Requirement 11.4.
8. WHEN the Open_Food_Facts_API responds with an HTTP status outside the 200-299 range, THE Barcode_Repository SHALL surface the failure as a `ServerException` whose message includes the HTTP status and the requested barcode, SHALL NOT attempt to parse the response body as an Off_Lookup_Response, and SHALL NOT retry automatically.
9. THE Barcode_Repository SHALL NOT cache Open_Food_Facts_API responses to disk in this spec; the React Native predecessor's `productLookupService` cache layer is explicitly out of scope and is deferred to a future spec. The Barcode_Repository SHALL expose its `lookupOpenFoodFacts(barcode)` method through a single Dart abstract class so that a future cache decorator can wrap the implementation as a one-file change without touching the Barcode_Notifier or any presentation file.
10. THE Barcode_Repository SHALL NOT consume the cook-smart Backend_API barcode routes `GET /api/v1/barcode/lookup/:barcode` or `POST /api/v1/barcode/scan-to-pantry`, because the React Native predecessor calls Open_Food_Facts directly and Foundation Requirement 9.3 forbids changing the Backend_API surface this migration consumes.

### Requirement 5: Cook-Smart Backend Ingredient Add Contract

**User Story:** As an authenticated user, I want the resolved scanned product to be persisted to my pantry by exactly the cook-smart endpoint the React Native app already consumes, so that the migration ships against the real backend without proposing endpoint changes.

#### Acceptance Criteria

1. WHEN the user confirms adding a Scanned_Product to the pantry, THE Barcode_Repository SHALL issue a `POST` to the path `/api/v1/ingredients` against the foundation-resolved Backend_API base URL, with `requiresAuth` set to `true` so the Foundation_Phase's `AuthInterceptor` attaches the JWT minted by the Auth_Feature, and SHALL apply the foundation-default timeouts (10-second connect, 15-second receive per Foundation Requirement 4.5) to the request.
2. THE Barcode_Repository SHALL build the request body from the Ingredient_To_Add domain model with exactly the following JSON fields, all camelCase to match the existing React Native client and `backend/src/routes/ingredients.ts` POST handler:
   - `customName` (String, the Scanned_Product's resolved name, maximum 200 characters after trimming, non-empty after trimming).
   - `category` (String, the Scanned_Product's resolved category or the literal string `"other"` when no category was resolved).
   - `quantity` (Number, defaulting to `1` when the user does not override, must be greater than 0 and less than or equal to 9999).
   - `unit` (String, defaulting to `"piece"` when the user does not override, maximum 32 characters).
   - `notes` (String, set to the literal pattern `"Added via barcode scan (<barcode>)"` so the React Native pantry's existing audit trail is preserved, maximum 500 characters total).
   The body SHALL NOT include `ingredientId`, `expirationDate`, or any other field, because the Scanned_Product is by definition new to the user and expiration management is out of scope.
3. THE Barcode_Repository SHALL accept any HTTP success response in the range 200 through 299 inclusive as a successful add, with 201 being the expected status returned by `backend/src/routes/ingredients.ts`'s POST handler.
4. WHEN a 200 or 201 response is received from the Ingredient_Endpoint, THE Barcode_Repository SHALL parse the response body as Ingredient_Add_Response by reading the top-level field `message` (String, optional) and the top-level field `ingredient` (JSON object, optional). The Barcode_Repository SHALL NOT attempt to parse the response as the Foundation_Phase's canonical `{ success, message, data }` envelope, because the Ingredient_Endpoint does not return that envelope, applying the same feature-local parsing approach Auth Decision 1 established for the auth endpoints.
5. WHEN the parsed Ingredient_Add_Response indicates success (any 2xx HTTP status with a JSON-object body), THE Barcode_Repository SHALL resolve the operation with no further side effects on `SecureStorage` and SHALL NOT cache the added ingredient locally in this spec.
6. IF a 200 or 201 response is received from the Ingredient_Endpoint and the response body is not a JSON object, OR `message` is present but is not a string, OR `ingredient` is present but is not a JSON object, THEN THE Barcode_Repository SHALL still resolve the operation as success because the user-visible add-to-pantry side effect has already occurred on the backend, and SHALL surface the malformed-body fact only to a logging hook (a top-level `void Function(String)` registered via the `Barcode_Api_Client` constructor), not to the Barcode_Notifier.
7. WHEN the Ingredient_Endpoint responds with `400` and a body containing `{ error, details }` (the Express-validator failure shape used by `backend/src/routes/ingredients.ts`), THE Barcode_Repository SHALL surface the failure as a `ValidationException` whose message is built from the response's `error` field followed by a comma-separated summary of the `details` array (each detail truncated to 120 characters, the full summary truncated to 500 characters), and SHALL NOT retry the request.
8. WHEN the Ingredient_Endpoint responds with `401`, THE Foundation_Phase's `ErrorInterceptor` SHALL run its existing clear-and-redirect path (Foundation Requirement 4.10) per the Auth_Feature's wiring (Auth Requirement 7.3), and the Barcode_Repository SHALL surface the resulting `UnauthorisedException` to the Barcode_Notifier, which SHALL transition Scan_State to `ScanFailed` with a `sessionExpired` sub-reason. No backend changes are required to support this behaviour because the Auth_Feature's overrides already close the loop.
9. WHEN the Ingredient_Endpoint responds with any 4xx status other than 400 or 401 (for example 403, 404, 409, 422, 429), THE Barcode_Repository SHALL surface the failure as a `ValidationException` whose message includes the HTTP status, a generic explanatory phrase, and the requested barcode, and SHALL NOT retry the request.
10. WHEN the Ingredient_Endpoint responds with `500` or any other 5xx status, THE Barcode_Repository SHALL surface the failure as a `ServerException` whose message includes the HTTP status and the requested barcode for diagnostic clarity, and SHALL NOT retry the request.
11. WHEN the Ingredient_Endpoint request fails with a transport-level error (connect timeout, receive timeout, DNS failure, connection refused, TLS handshake failure), THE Barcode_Repository SHALL surface the failure as a `NetworkException` whose message identifies the failure category and the offending barcode, and SHALL NOT retry automatically; retry SHALL be initiated only by an explicit user action per Requirement 11.8.
12. THE Barcode_Repository SHALL NOT issue a request to any path other than `/api/v1/ingredients` against the Backend_API. The Backend_API routes `POST /api/v1/ingredients/custom`, `GET /api/v1/ingredients/search`, `POST /api/v1/ingredients/pantry`, and `POST /api/v1/barcode/scan-to-pantry` are out of scope for this spec.

### Requirement 6: Authenticated-Request Precondition

**User Story:** As the solo developer, I want the barcode scanner to require an authenticated user before the camera even starts, so that an unauthenticated user is redirected to login rather than scanning a barcode they have no session to persist.

#### Acceptance Criteria

1. WHEN the user attempts to enter the BarcodeScannerScreen via any router path AND the Auth_Feature's `authStateProvider` resolves to `false`, THE Foundation_Phase's `routerProvider` SHALL apply its existing redirect rule (Foundation Requirement 5.7) and SHALL redirect the user to `/auth/login` within 500 milliseconds, before the BarcodeScannerScreen widget is constructed.
2. THE Barcode_Feature SHALL NOT add any custom redirect rule to the foundation's `routerProvider`; it SHALL rely exclusively on the Auth_Feature's `authStateProvider` override (Auth Requirement 7.2) to drive the existing redirect rule cited in criterion 1.
3. WHEN the Barcode_Notifier transitions to `ScanIdle`, THE Barcode_Feature SHALL read the Auth_Feature's `authNotifierProvider` exactly once per transition, and the read SHALL complete within 100 milliseconds of the transition.
4. IF the Auth_State observed by criterion 3 is anything other than `AuthAuthenticated`, THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with the sub-reason `notAuthenticated` within 200 milliseconds. This is a defence-in-depth check; the router redirect of criterion 1 is the primary gate.
5. WHILE a Scan_Session is in flight (the Scan_State is one of `ScanRequestingPermission`, `ScanCameraActive`, `ScanLookingUp`, `ScanProductFound`, `ScanProductNotFound`, `ScanAdding`), IF the Auth_Notifier emits `AuthUnauthenticated` for any reason (a 401 from the Ingredient_Endpoint per Requirement 5.8, an explicit logout from another screen, or a Session_Restore failure), THEN THE Barcode_Notifier SHALL transition the Scan_State to `ScanFailed` with the sub-reason `sessionExpired` within 1 second of the `AuthUnauthenticated` emission, and SHALL release the camera per Requirement 2.8.
6. THE Barcode_Repository SHALL NOT read, write, or reference the JWT under any storage key (including but not limited to `'jwt'`, `'auth_user'`, and `'refreshToken'`) directly; the JWT SHALL be attached to outgoing requests exclusively by the Foundation_Phase's `AuthInterceptor` per Foundation Requirement 4.2, with the Barcode_Repository setting `requiresAuth: true` per Requirement 5.1.
7. THE Barcode_Repository SHALL NOT contain any `import` statement whose path begins with `mobile/lib/features/auth/`. It SHALL interact with auth state only through the foundation-exposed `authNotifierProvider` symbol re-exported by the Auth_Feature into a foundation-visible location per Auth Requirement 7, and through the `requiresAuth` flag on outgoing requests.

### Requirement 7: Domain Models

**User Story:** As the solo developer, I want one Scanned_Product type that captures every field this spec consumes from the Open_Food_Facts_API and one Ingredient_To_Add type that captures every field the Ingredient_Endpoint accepts, so that the boundary between transport and presentation is type-checked.

#### Acceptance Criteria

1. THE Scanned_Product domain model SHALL declare the following non-null fields: `barcode` (String, the validated 8-to-13-digit string from Requirement 3.1, exactly matching the regex `^[0-9]{8,13}$`), `name` (String, the resolved product name per Requirement 4.4, length between 1 and 200 characters inclusive after the resolution rules of that requirement are applied).
2. THE Scanned_Product domain model SHALL declare the following nullable fields: `brand` (String?, length 1 to 200 characters when non-null), `category` (String?, length 1 to 200 characters when non-null), `imageUrl` (String?, length 1 to 2048 characters when non-null).
3. THE Scanned_Product domain model SHALL be implemented as a `final class` with `const` constructor, value-equality (`==` and `hashCode` by all fields declared in criteria 1 and 2), and `copyWith` covering every field declared in criteria 1 and 2. The `copyWith` method SHALL use the same "sentinel for nullable fields" pattern the Auth_Feature's User model established in `flutter-port-auth/design.md` so callers can distinguish "argument not passed" from "argument passed as null" for the three nullable fields.
4. THE Ingredient_To_Add domain model SHALL declare the following non-null fields: `barcode` (String, matching the regex of criterion 1), `customName` (String, length 1 to 200 characters after trimming, non-empty after trimming), `category` (String, length 1 to 100 characters), `quantity` (num, greater than 0 and less than or equal to 9999), `unit` (String, length 1 to 32 characters).
5. THE Ingredient_To_Add domain model SHALL provide a method `toBackendJson()` that emits the JSON body shape mandated by Requirement 5.2 with the `notes` field synthesised from `barcode` per the literal pattern in that requirement.
6. IF the Ingredient_To_Add domain model's `toBackendJson()` is called when any field declared in criterion 4 is outside the documented bounds (for example `customName` is empty after trimming, or `quantity` is zero or negative, or `unit` is longer than 32 characters), THEN `toBackendJson()` SHALL throw a `StateError` with a message identifying the offending field and SHALL NOT emit a partial JSON body.
7. THE Ingredient_To_Add domain model SHALL provide a factory `Ingredient_To_Add.fromScannedProduct(Scanned_Product, {num quantity = 1, String unit = 'piece'})` that maps a Scanned_Product to a default-shaped Ingredient_To_Add, applying the rule "category defaults to the literal string `'other'` when the Scanned_Product's category is null". The user-confirmation flow MAY override `quantity` and `unit` before calling `toBackendJson()` per Requirement 9.6.
8. THE Scan_State sealed type SHALL declare exactly ten variants in this order: `ScanIdle` (no payload), `ScanRequestingPermission` (no payload), `ScanPermissionDenied` (a `reason` field of an enum sub-type with values `denied`, `permanentlyDenied`, and `unavailable`), `ScanCameraActive` (no payload), `ScanLookingUp` (a `barcode` String field), `ScanProductFound` (a `Scanned_Product` field), `ScanProductNotFound` (a `barcode` String field), `ScanAdding` (an `Ingredient_To_Add` field), `ScanAdded` (an optional `addedIngredientName` String field, populated from the Ingredient_Add_Response per Requirement 5.4 when available), and `ScanFailed` (a `reason` enum sub-type field with values `network`, `server`, `validation`, `notAuthenticated`, `sessionExpired`, `cameraUnavailable`, plus a `description` String field).
9. THE Scan_State sealed parent and each of its ten variants SHALL be implemented as `final class` with `const` constructor and value-equality, so that the Riverpod notifier emits `==`-equal states without re-rendering when nothing has changed.
10. IF a `product` JSON object received from the Open_Food_Facts_API is missing every field listed in Requirement 4.4, THEN the Off_Lookup_Response SHALL still construct a Scanned_Product whose `name` is the literal string `"Unknown Product"`, because the React Native predecessor's behaviour is to surface "Unknown Product" rather than to fail; this is a deliberate UX trade-off and is preserved here for parity.

### Requirement 8: Riverpod Provider Graph

**User Story:** As the solo developer, I want the Barcode_Feature's providers to compose cleanly with the foundation and the Auth_Feature, so that adding a new feature provider does not require re-wiring the foundation.

#### Acceptance Criteria

1. THE Barcode_Feature SHALL declare a `barcodeApiClientProvider` of type `Provider<BarcodeApiClient>` in `mobile/lib/core/network/barcode_api_client.dart`, returning a `DioBarcodeApiClient` constructed from the foundation's `dioProvider`. This provider lives under `core/network/` for the same reason the Auth_Feature's `authApiClientProvider` does (Auth Decision 4): to keep `package:dio` confined to that directory while exposing a feature-shaped surface.
2. THE Barcode_Feature SHALL declare a `barcodeRepositoryProvider` of type `Provider<BarcodeRepository>` in `mobile/lib/features/barcode/data/barcode_repository.dart`, with the BarcodeRepository constructed from `barcodeApiClientProvider`.
3. THE Barcode_Feature SHALL declare a `barcodeNotifierProvider` as an auto-disposing `AsyncNotifierProvider<BarcodeNotifier, ScanState>.autoDispose` in `mobile/lib/features/barcode/presentation/barcode_notifier.dart`, where `ScanState` is the sealed type defined in Requirement 7.8.
4. THE Barcode_Feature SHALL NOT introduce any override of a foundation provider in `mobile/lib/main.dart`, because every provider it needs is local to the Barcode_Feature; the Auth_Feature's overrides (Auth Requirement 7.4) are the only feature-driven overrides applied to the root `ProviderScope` at the time this spec ships.
5. WHEN a widget under `mobile/lib/features/barcode/presentation/` reads scan state, THE widget SHALL read from `barcodeNotifierProvider`.
6. THE widget reading from `barcodeNotifierProvider` per criterion 5 SHALL render the three `AsyncValue<ScanState>` states (loading, error, data) using `AsyncValue<T>.when` with a non-null callback for each per Foundation Requirement 3.5.
7. WHEN the Barcode_Notifier is first constructed by Riverpod, THE Barcode_Notifier SHALL emit `ScanIdle` as its initial state.
8. THE Barcode_Notifier SHALL NOT issue any Open_Food_Facts_API or Backend_API request until the user explicitly invokes `startSession`, `submitBarcode`, or `confirmAdd`, and the quiescence invariant SHALL hold for the entire lifetime of any Barcode_Notifier instance until the first such invocation.
9. THE Barcode_Feature SHALL NOT use Riverpod's `keepAlive` modifier on `barcodeNotifierProvider`, because a half-completed Scan_Session SHALL NOT survive navigation.
10. WHEN the BarcodeScannerScreen is popped from the router stack, THE Barcode_Notifier SHALL be disposed by Riverpod's auto-dispose mechanism within 1 second, and the `dispose` callback SHALL release the camera per Requirement 2.8.
11. IF the Barcode_Notifier is disposed while an Open_Food_Facts_API or Ingredient_Endpoint request is in flight, THEN the in-flight request SHALL be cancelled via the Dio `CancelToken` mechanism within 500 milliseconds of disposal, and the Barcode_Notifier SHALL NOT mutate any state, render any UI, or call any side-effecting method after disposal completes.

### Requirement 9: Barcode Scanning UX

**User Story:** As a user, I want a clear and forgiving scanner UI that gives me feedback the moment a barcode is read and lets me bail out to manual entry whenever I want, so that I can add an ingredient quickly even when scanning is awkward.

#### Acceptance Criteria

1. WHEN the BarcodeScannerScreen is constructed and the Camera_Permission_State is `granted`, THE BarcodeScannerScreen SHALL render a full-screen camera preview with a centred rectangular viewfinder overlay measuring 250 logical pixels on a side, with four corner markers drawn in a colour token from `app_colours.dart`, and SHALL display the instruction text `"Point camera at barcode"` below the viewfinder.
2. WHEN the BarcodeScannerScreen is constructed and the Camera_Permission_State is anything other than `granted`, THE BarcodeScannerScreen SHALL NOT render the camera preview or the viewfinder overlay, and SHALL render the appropriate error region per Requirement 11.1, 11.2, or 11.3 instead.
3. WHEN the camera detects a candidate barcode that passes the validation rule of Requirement 3.1, THE Barcode_Feature SHALL transition Scan_State to `ScanLookingUp` within 100 milliseconds of detection, SHALL trigger a single haptic-feedback impulse of "medium" intensity, and SHALL render a non-blocking loading card with the text `"Looking up product..."` centred on the screen.
4. WHILE the Scan_State is `ScanLookingUp`, THE Barcode_Feature SHALL ignore further barcode-detection callbacks from the camera. This SHALL be implemented as a debounce in the Barcode_Notifier rather than by stopping the camera, so that the camera does not need to be restarted on a "try again" outcome.
5. WHEN the Scan_State transitions to `ScanProductNotFound`, THE Barcode_Feature SHALL render a modal alert with the title `"Product Not Found"`, the body `"This product is not in our database. You can add it manually."`, and exactly two action buttons: `"Manual Entry"` (which closes the alert and pushes the ManualBarcodeEntryScreen) and `"Try Again"` (which transitions Scan_State back to `ScanCameraActive` and resumes barcode-detection callbacks per criterion 4).
6. WHEN the Scan_State transitions to `ScanProductFound`, THE Barcode_Feature SHALL push the ScannedProductConfirmationScreen, which SHALL display the Scanned_Product's `name`, `brand` (when non-null), `category` (when non-null), and `imageUrl` rendered via `cached_network_image ^3.3.1` (Foundation Requirement 10.7) when non-null, plus editable fields for `quantity` (default `1`) and `unit` (default `"piece"`), plus an `"Add to Pantry"` button.
7. WHEN the user taps `"Add to Pantry"` on the ScannedProductConfirmationScreen, THE Barcode_Feature SHALL transition Scan_State to `ScanAdding`, SHALL invoke the Barcode_Repository's `addIngredient` operation per Requirement 5.1 with a 15-second receive timeout per Foundation Requirement 4.5, and SHALL disable the `"Add to Pantry"` button until the operation resolves with success or failure.
8. IF the `addIngredient` operation per criterion 7 fails with any `ApiException` subtype, THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` per Requirement 11.6, 11.7, or 11.8, SHALL re-enable the `"Add to Pantry"` button, SHALL preserve the user's typed `quantity` and `unit` values verbatim, and SHALL keep the ScannedProductConfirmationScreen mounted.
9. WHEN the Scan_State transitions to `ScanAdded`, THE Barcode_Feature SHALL render a non-blocking success banner with the text `"<addedIngredientName> has been added to your inventory"` (using the value from Requirement 7.8 when available, falling back to the Scanned_Product's `name` otherwise), the banner SHALL remain visible for 3 seconds before auto-dismissing, and the BarcodeScannerScreen, ScannedProductConfirmationScreen, and any associated modals SHALL pop from the router stack within 1 second of the transition.
10. THE BarcodeScannerScreen SHALL render exactly two control buttons at the bottom of the screen at all times: `"Cancel"` (which pops the BarcodeScannerScreen) and `"Manual Entry"` (which closes the camera and pushes the ManualBarcodeEntryScreen). The buttons SHALL remain interactive in every Scan_State except `ScanAdding`.
11. WHEN the user navigates away from the BarcodeScannerScreen by tapping `"Cancel"`, by using the system back gesture, or by switching apps, THE Barcode_Feature SHALL transition Scan_State to `ScanIdle`, release the camera per Requirement 2.8, and dispose the BarcodeNotifier per Requirement 8.10.
12. THE BarcodeScannerScreen and the ManualBarcodeEntryScreen SHALL NOT use a `FutureBuilder` to render any state, because Foundation Requirement 3.6 forbids it and the architecture script enforces the ban; every async piece of state SHALL be expressed as an `AsyncValue<T>` Riverpod provider read with `AsyncValue<T>.when`.

### Requirement 10: Manual-Entry Fallback

**User Story:** As a user whose camera is denied, broken, or just inconvenient right now, I want to type a barcode in by hand and have the same lookup-and-add flow run, so that I am not blocked from adding an ingredient.

#### Acceptance Criteria

1. THE ManualBarcodeEntryScreen SHALL render a single text field that accepts only ASCII digits per Requirement 3.6, with `keyboardType` set to numeric, `maxLength` set to 13, and the label `"Enter Barcode"`.
2. THE ManualBarcodeEntryScreen SHALL render a `"Lookup Product"` submit button that is disabled while the input field is empty AND while the Scan_State is `ScanLookingUp`, and a visible progress indicator adjacent to the submit button SHALL be rendered while the Scan_State is `ScanLookingUp` so the in-flight state is observable.
3. WHEN the user submits a manually entered barcode that matches the regex of Requirement 3.1, THE Barcode_Notifier SHALL transition Scan_State to `ScanLookingUp` within 200 milliseconds of submission and SHALL invoke the same Open_Food_Facts_API lookup the camera path uses per Requirement 4.
4. IF the user submits a manually entered barcode that does not match the regex of Requirement 3.1, THEN THE Barcode_Notifier SHALL render an inline error per Requirement 3.5, SHALL NOT transition Scan_State to `ScanLookingUp`, and SHALL NOT invoke the Open_Food_Facts_API lookup.
5. WHEN a manually entered barcode resolves to `ScanProductFound`, THE Barcode_Feature SHALL push the ScannedProductConfirmationScreen, with the same UX defined in Requirement 9.6, so that camera-scanned and manually-entered confirmations share one code path.
6. WHEN a manually entered barcode resolves to `ScanProductNotFound`, THE ManualBarcodeEntryScreen SHALL render an inline non-blocking message above the input field with the text `"Product not found in the Open Food Facts database. Try a different barcode or add the ingredient by hand from the pantry screen."`, SHALL leave the input field populated so the user can correct a typo, SHALL NOT invoke the modal alert defined in Requirement 9.5, and SHALL clear the message when the user edits the input field or submits a new lookup.
7. THE Barcode_Feature SHALL make the ManualBarcodeEntryScreen reachable from every Scan_State except `ScanAdding`, regardless of the Camera_Permission_State; the established entry paths are the BarcodeScannerScreen's `"Manual Entry"` button per Requirement 9.10 and the BarcodeScannerScreen's `"Open Settings"` affordance per Requirement 2.5 when camera permission is `permanentlyDenied`. Future entry paths added to the Mobile_App SHALL push the ManualBarcodeEntryScreen using the same `barcodeNotifierProvider` so a single Barcode_Notifier instance is reused across paths.
8. IF the manual-entry lookup fails with `NetworkException` per Requirement 4.7 or `ServerException` per Requirement 4.6 or 4.8, THEN THE ManualBarcodeEntryScreen SHALL render an inline non-blocking error message above the input field, SHALL preserve the user's typed input verbatim, SHALL transition Scan_State out of `ScanLookingUp`, SHALL re-enable the submit button, and SHALL clear the error message when the user edits the input field or submits a new lookup.
9. WHEN the ManualBarcodeEntryScreen is the only entry path because the Camera_Permission_State is `unavailable` per Requirement 2.6, THE Barcode_Feature SHALL render an informational note above the input field with the text `"Camera is unavailable; enter the barcode by hand."`, so the user understands why the camera path is missing.

### Requirement 11: Error Handling Matrix

**User Story:** As a user, I want every failure mode to surface a clear message and a recovery action, so that I am never stuck staring at a blank screen.

#### Acceptance Criteria

1. WHILE Camera_Permission_State is `denied` (one-time refusal), THE Barcode_Feature SHALL render an inline error region on the BarcodeScannerScreen containing the text `"Camera access is needed to scan barcodes."` and a `"Grant Permission"` button that re-invokes the permission request flow per Requirement 2.4.
2. WHILE Camera_Permission_State is `permanentlyDenied` (the user has selected "Don't ask again" or has denied at the OS level), THE Barcode_Feature SHALL render an inline error region containing the text `"Camera access is blocked. Please enable it in Settings."` and an `"Open Settings"` button that calls the device settings page via the foundation-pinned `url_launcher ^6.3.0` package (Foundation Requirement 10.6).
3. WHILE Camera_Permission_State is `unavailable`, THE Barcode_Feature SHALL render an inline error region containing the text `"Camera is not available on this device."`, SHALL NOT render the camera preview, SHALL NOT render the `"Grant Permission"` button, and SHALL render a primary-styled `"Use Manual Entry"` button that, when tapped, pushes the ManualBarcodeEntryScreen per Requirement 10.7.
4. IF the Open_Food_Facts_API request fails with `NetworkException`, THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `network` and SHALL render a modal alert with the title `"Lookup Failed"`, a body identifying the failure as a network error, and exactly two action buttons: `"Retry"` (which re-invokes the lookup with the same barcode, up to a maximum of 3 retry attempts per Scan_Session, after which the `"Retry"` button SHALL be disabled and a tooltip SHALL display the text `"Retry limit reached. Try Manual Entry."`) and `"Manual Entry"` (which pushes the ManualBarcodeEntryScreen with the barcode pre-populated).
5. IF the Open_Food_Facts_API request fails with `ServerException` per Requirement 4.6 or 4.8, THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `server` and SHALL render a modal alert with the title `"Lookup Failed"`, a body identifying the failure as a server error, and the same two action buttons defined in criterion 4 with the same 3-attempt retry limit.
6. IF the Ingredient_Endpoint request fails with `ValidationException` per Requirement 5.7 or 5.9, THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `validation` and SHALL render the validation message in an inline error region on the ScannedProductConfirmationScreen, leaving the user's typed `quantity` and `unit` values intact so the user can correct them.
7. IF the Ingredient_Endpoint request fails with `UnauthorisedException` per Requirement 5.8, THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `sessionExpired`, and the foundation's `routerProvider` SHALL redirect to `/auth/login` per Foundation Requirement 5.9 driven by the Auth_Notifier emitting `AuthUnauthenticated` per Auth Requirement 8.4. The Barcode_Feature SHALL NOT render its own session-expired modal because the redirect renders the LoginScreen with the Auth_Feature's existing inline error.
8. IF the Ingredient_Endpoint request fails with `ServerException` per Requirement 5.10 or `NetworkException` per Requirement 5.11, THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with the appropriate sub-reason (`server` or `network`) and SHALL render a modal alert on the ScannedProductConfirmationScreen with the title `"Add Failed"`, a body identifying the failure category, and a `"Retry"` button that re-invokes `addIngredient` with the same Ingredient_To_Add up to a maximum of 3 retry attempts per confirmation session, after which the `"Retry"` button SHALL be disabled.
9. THE Barcode_Feature SHALL NOT render the literal text of an underlying `DioException`, an HTTP status code by itself, or a stack trace anywhere in the user-facing UI; every error message rendered to the user SHALL come from the static strings enumerated in this Requirement, from the Auth_Feature's existing strings (for session-expired), or from the Backend_API's `error` and `details` fields (for `ValidationException` per Requirement 5.7).
10. THE Barcode_Feature SHALL emit every captured error to the foundation-pinned Firebase Crashlytics integration (Foundation Requirement 16) by allowing `ServerException`, `NetworkException`, `ValidationException`, and `UnauthorisedException` to propagate to the foundation's `FlutterError.onError` and `PlatformDispatcher.instance.onError` handlers as non-fatal Dart errors. The Barcode_Feature SHALL NOT directly call any Crashlytics API; it SHALL rely on the foundation's existing wiring.
11. WHEN the user dismisses a modal alert rendered per criterion 4, 5, or 8 (via the system back gesture, a tap outside the modal, or any close affordance on the modal), THE Barcode_Feature SHALL close the modal and leave the underlying screen in its pre-error state with Scan_State remaining `ScanFailed` until the user takes a recovery action or navigates away from the screen.

### Requirement 12: Performance and Responsiveness

**User Story:** As a user, I want the scanner to be snappy and the lookups to be bounded, so that the feature feels production-grade rather than experimental.

#### Acceptance Criteria

1. WHEN the user invokes the scan action and the Camera_Permission_State is already `granted`, THE Barcode_Feature SHALL initiate camera activation within 2000 milliseconds of the action.
2. IF the camera preview has not produced its first frame within 2000 milliseconds of camera activation initiation per criterion 1, THEN THE Barcode_Feature SHALL render a non-blocking loading indicator centred on the BarcodeScannerScreen with the text `"Starting camera..."` until either the first frame is produced or a hard failure surfaces per criterion 3.
3. IF the underlying `mobile_scanner ^5.1.1` API surfaces a hard failure during camera activation (the package's documented error callbacks fire with a non-recoverable error code), THEN THE Barcode_Feature SHALL transition Scan_State to `ScanFailed` with sub-reason `cameraUnavailable` and a `description` field identifying the failure category within 200 milliseconds of the failure callback firing.
4. WHEN the camera detects a valid barcode in frame, THE Barcode_Feature SHALL transition Scan_State to `ScanLookingUp` within 100 milliseconds of the detection callback per Requirement 9.3.
5. THE Barcode_Feature SHALL apply the per-request timeout overrides defined in Requirement 4.2 (5-second connect, 10-second receive) to every Open_Food_Facts_API call.
6. THE Barcode_Feature SHALL apply the foundation-default timeouts (10-second connect, 15-second receive per Foundation Requirement 4.5) to every Ingredient_Endpoint call, so the timeouts SHALL be uniform across cook-smart endpoints.
7. WHEN the Scan_State is `ScanLookingUp`, THE Barcode_Feature SHALL ignore every barcode-detection callback received from the camera and SHALL defer the next allowed lookup until either the Scan_State has returned to `ScanCameraActive` (via "Try Again") or the BarcodeScannerScreen has been popped and re-pushed.
8. WHILE a Scan_Session is in flight, THE Barcode_Feature SHALL apply a soft rate limit of at most one Open_Food_Facts_API request per 1000 milliseconds, deferring any second request that arrives within the 1000-millisecond window until the window has elapsed, matching the React Native predecessor's `MIN_REQUEST_INTERVAL` constant.
9. WHEN the Barcode_Notifier transitions out of `ScanCameraActive` for any reason, THE Barcode_Feature SHALL release the camera within 500 milliseconds of the transition per Requirement 2.8.

### Requirement 13: Architectural Compliance

**User Story:** As the solo developer, I want the Barcode_Feature to ship without relaxing or amending the Foundation_Phase's enforcement scripts or the Auth_Feature's transport-seam pattern, so that the migration's invariants stay machine-checked.

#### Acceptance Criteria

1. WHEN any of the four scripts `dart run mobile/tool/check_architecture.dart`, `dart run mobile/tool/check_structure.dart`, `dart run mobile/tool/check_packages.dart`, or `dart run mobile/tool/check_secrets.dart` is invoked from the repo root with no arguments, THE Barcode_Feature SHALL produce a process exit code of 0 from the invocation, and the bytes of the four script files SHALL be byte-for-byte identical to their state in the most recent merged commit of the `flutter-migration-architecture` spec.
2. THE Barcode_Feature SHALL NOT add any new Dart package to `mobile/pubspec.yaml`, because the Foundation_Phase's committed package list (Foundation Requirement 10) and the Auth_Feature's `glados ^1.1.6` addition for property-based testing (Auth Requirement 13.2) together cover every dependency this spec needs. In particular, `mobile_scanner ^5.1.1` (Foundation Requirement 10.3) is the camera and barcode-decoder dependency, `cached_network_image ^3.3.1` (Foundation Requirement 10.7) is the Scanned_Product image renderer, and `url_launcher ^6.3.0` (Foundation Requirement 10.6) is the device-settings opener.
3. WHEN `flutter analyze` is invoked from the `mobile/` directory with no arguments, THE Barcode_Feature SHALL produce a process exit code of 0, zero error-level diagnostics, and zero warning-level diagnostics under the `very_good_analysis` ruleset committed by Foundation Requirement 10.8. The use of `// ignore:` directives in any file under `mobile/lib/features/barcode/` or in the Barcode_Api_Client seam files SHALL be limited to a maximum of 3 directives total, each justified by a comment immediately above the directive explaining why the lint cannot be satisfied.
4. WHEN `flutter test` is invoked from the `mobile/` directory with no arguments, THE Barcode_Feature SHALL produce a process exit code of 0, zero failed tests, zero errored tests, and zero skipped tests across every `_test.dart` file required by Requirement 1.8.
5. IF a future requirement of this spec implies a backend change to the Ingredient_Endpoint path, the request body shape, the response body shape, the JWT-based authentication flow, or the addition of any new cook-smart Backend_API route, THEN THE Barcode_Feature SHALL reject the change per Foundation Requirement 9.8 and SHALL file a separate backend issue rather than absorb the change into the migration.
6. THE Barcode_Feature SHALL exercise at minimum the following three properties via the `glados ^1.1.6` property-based-testing package introduced by the Auth_Feature (Auth Requirement 13.2), with at least 100 generator-produced inputs per property per `flutter test` run, and SHALL NOT substitute regular example-based unit tests for these three properties because the value of property-based coverage is in the generated input space rather than the assertion shape:
   - (a) the round-trip property `Off_Lookup_Response.fromJson(scannedProduct.toOpenFoodFactsLikeJson()).product == scannedProduct` for every Scanned_Product the generator produces;
   - (b) the parser-strictness property "every malformed Open_Food_Facts_API body raises `ServerException`" per Requirement 4.6;
   - (c) the validation property "every barcode whose digit string fails the regular expression of Requirement 3.1 is rejected by `Barcode_Repository.lookupOpenFoodFacts` without an HTTP request being issued".
7. THE Barcode_Feature's `mobile/lib/core/network/barcode_api_client.dart` file SHALL exist and SHALL contain an abstract Dart class `BarcodeApiClient` plus a concrete Dio-backed adapter `DioBarcodeApiClient` that implements that abstract class. The presence of this file together with the Auth_Feature's `auth_api_client.dart` SHALL establish two instances of the feature-shaped transport-seam pattern documented in Auth Decision 4, confirming the pattern as the established convention for future per-feature specs.
